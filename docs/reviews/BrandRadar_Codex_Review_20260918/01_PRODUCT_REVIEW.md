# Brand Radar｜产品与实现评议

## 核心判断

**下一轮值得投入的是连续工作体验：让人少管理画布，多推进作品。** 现有能力已覆盖生成、局部改稿、富内容、分组连线、语音、保存与导出。继续增加对象类型、模板和技术入口，会扩大需要维护的状态组合；当前更直接的收益来自阅读、输入、修改与恢复的可靠性。

本评议以当前原生 iPhone 产品为主要迭代对象，网页作为调查与长文工作的保留入口。依据为产品文档与已查阅的主流程源码，未完成运行态视觉审查。具体证据见 E01—E16。

## 一、目前实际上存在两条产品方向

PRD 描述的是有品牌背景、公开材料和调查工具的营销企划搭档；最新首页与移动端介绍强调口述成图、自由画布、照片手绘与通用内容组织，甚至支持三幕剧本任务。两条路线都能解释部分现有功能，但它们对下一步投资的要求不同。[E01—E04]

### 品牌企划路线

价值集中在材料质量、品牌参与理由、反例、修改之后是否改变具体做法，以及能否形成可讨论的工作稿。画布服务于这些判断。继续走这条路线，需要逐步处理移动端的品牌背景和取材能力；现有 Web 调查能力有保留价值。

### 通用思考画布路线

价值集中在表达是否忠实、关系是否清楚、人工修正是否轻松、内容是否易于找回。营销知识可以成为一个使用场景。继续走这条路线，会面对更广的编辑、搜索、导入和组织需求。

**本轮建议先收窄工作过程，保持内容场景开放。** 暂用以下工作定义指导开发：

> 把一段想法和已有材料，整理成能阅读、能继续修改、能保留原始依据的结构化工作稿。

这项定义覆盖品牌企划与内容构思共有的需求。它尚不等于决定长期定位。不要据此自动改名、删去营销能力、重写所有提示词，或启动通用白板的全面建设。

在下一轮使用中，选择一个真实品牌小企划和一个真实内容构思项目，各自连续使用多次。观察哪里需要画布，哪里需要阅读，什么内容会在第二天继续打开。再决定强化行业深度还是通用组织能力。仅凭“生成了一张图”不足以检验持续使用价值。

## 二、应保留的基础

现有实现对作品控制权已有实质投入：旧卡复用 ID；人的布局和采用状态受到保护；条件撤销避免直接覆盖后续手改；Beta 待确认结果可恢复；富内容与原始附件得以保留。画布也已有几何缓存、屏外剔除和清单／表格的结构化预览。[E03、E07—E13]

这些能力不要在 UI 重构中丢失。下一轮无需替换 SwiftUI／UIKit 组合，无需重新选无限画布库，无需换成多 Agent。仍应保留公开材料调查、原文关联、品牌底稿显式保存，以及现有本地导出能力。[E02—E03]

桌面和手机可以承担不同工作：桌面读较多材料、调查与比较；手机捕捉想法、阅读局部、推进某个方向。此分工是本轮资源安排建议，跨设备无缝接续尚需单独验证，不能暗示当前已经拥有完整同步能力。

## 三、优先处理的源码问题

下列项目区分“源码可确认的行为”和“尚待观察的使用后果”。它们并非都代表运行时故障。

### 1. 放下／恢复没有恢复同一份结构

`BoardStore.editCard` 在卡片进入 `archived` 时删除相邻连线，并移除分组成员关系。`CardEditor` 的恢复路径只将状态改回 `draft`，没有相应恢复逻辑。[E07、E09]

**确定的是**：按这条路径恢复，卡片原有的关系及归属不会随之自动回来。现有撤销可提供另一种恢复路径，因此这里不称为不可恢复的数据丢失。

**产品要求**：“放下”应当允许暂存一个方向并保留其结构信息。恢复时，对仍有效的端点和父组有条件还原；已删除或有冲突的对象应明确提示。不要为缺失的历史关系编造内容。

### 2. 取消编辑的含义被中途提交打破

`CardEditor` 使用本地编辑副本；但“内容转为节点”的回调先调用 `store.editCard`，再执行 `store.splitBlock`，从而提前持久化本地改动。顶部“取消”只关闭编辑器。[E07]

**复现路径**：改标题或正文 → 将一个内容块转为节点 → 取消 → 重开原卡。需要核对哪些改动已留在作品中。

首选小范围修复：将这类操作明确命名为“保存并转为节点”，显式提交后关闭当前编辑会话，并把相关改动记录为可撤销的一次操作。保存前的取消保留原稿。也可以采用编辑事务，但不应为这一处行为先扩建通用事务系统，更不能用整张画布快照覆盖异步写入。

### 3. 对话发送会自动关闭对话页

`ChatSheet` 发送后，只要 `busyBoardID != nil` 就清空输入、关闭键盘并 `dismiss()`。[E08]

这有让用户立即看到成图结果的意图，但连续三轮讨论会反复经历“打开对话—发送—被关闭”。是否令人困扰需要真机观察，代码路径本身明确。

建议将“发送”和“查看画布变化”分开：发送后保留当前面板状态；用户可以主动收起面板，或点击变化提示定位作品。此时必须同步处理面板占用的画布可见区域，避免留下一个遮住全部作品的永久聊天窗。

### 4. 阅读旧消息时可能被新回复拉到底部

`ChatSheet` 在消息数量、最后消息内容和运行状态变化时均调用 `scrollTo("end")`，未在已查阅实现中按用户当前位置判断。[E08]

建议只在用户接近底部时跟随滚动。向上阅读时保持位置，出现“有新回复”入口；点击后再跳到末尾。无需增加复杂聊天功能。

### 5. 分组选中状态缺少对应的输入提示

Agent 校验支持选中组；而聊天顶部提示依赖 `store.selectedCard`，该属性只查卡片数组，不能代表分组。[E07—E11]

这会造成系统能够限制一个组的修改范围，界面却未用同等方式展示该范围。建议统一“整张画布／某张卡片／某个分组”的选择上下文，并在请求发出时固定目标。原生多选目前主要用于画布操作，不顺带扩展成 AI 多对象编辑协议。

### 6. 缩放层级以卡片宽度决定，文字仍随画布缩小

`RadarCanvasView.draw` 整体缩放绘制上下文，`drawCard` 的正文使用 14 点世界坐标字号，标题为 23 点；显示与否主要按卡片映射到屏幕的宽度控制。[E12]

例如在 50% 缩放下，这段正文的几何显示尺寸约为 7 点。此计算来自绘制逻辑，尚未实测用户阅读效果。随着全貌包含更多内容，可读性风险会增加。

建议提供分层展示：远景看组与方向，中景看标题和简短预览，阅读状态用正常文字大小显示完整内容。不要要求用户把全貌里的微小正文当成主要阅读方式，也不要让低倍文字不断溢出卡片。

### 7. 部分高频控件的可点区域过小

画布原生上下文工具栏按钮设为 36×32 点，卡片颜色选择圆点为 32×32 点；部分顶部入口也小于 44 点。实际额外命中区域需要运行时核查。[E05、E07、E12]

将高频触摸区域至少扩到 44×44 点，图标本身可继续保持轻巧。Apple 的英文设计建议使用 points；不要把它与 Web 的 CSS 像素标准混用。[E16]

### 8. 原生画布库混合了全局文档和当前文档内容

`BoardLibrary` 列出全部当前模式画布后，又显示当前画布的“已放下”卡片。列表只显示模板与卡片数，未在该组件提供搜索、最近编辑时间或最近修改排序。[E07、E09]

建议画布库只承担文档查找；当前画布的已放下内容留在当前画布操作里。现有 `updated` 字段可以支持最近修改排序和日期展示，暂不需要文件夹树、标签体系或数据库迁移。

### 9. “查看新增”不能代表所有改稿结果

UIKit 画布的 `newIDs` 由对象 ID 的新增差集形成；“查看新增”据此定位。修改旧卡不属于新增对象。Beta 已有变化数量与确认机制，当前问题集中在普通改稿的结果导航。[E05、E12]

建议复用实际应用的修改差异，形成“修改了 2 张卡，新增 1 张”的结果条，支持逐项定位与撤销本轮。变化数以保存层实际应用的结果为准，不能直接相信模型自述的 summary。

## 四、UI 的重点：阅读层级与动作层级

继续保留 PRD 的暖白、墨绿和轻纸张层次。当前建议不包含品牌重做，也没有依据宣称实际截图已经达到或未达到某种审美水平。[E02、E07]

### 内容应当获得的层级

第一层：具体标题和正在讨论的判断。第二层：一小段足以识别内容的预览。第三层：来源、采用状态和其他辅助信息。

Web 卡片目前会同时显示中文类型、英文 eyebrow，以及创意卡上的解释性尾句。可以保留简短中文类型，把重复的英文说明和解释性装饰降级，从而把首要注意力留给标题与内容。[E15]

原生卡片的彩色目前允许用户自由选择；颜色无需承诺严密分类。保留文字和图标来表达来源类型、采用状态及选中状态，避免一个绿色同时承担多种未解释的含义。

### 动作应当获得的层级

输入与局部讨论是主入口；阅读、编辑、连接是选中后的动作；撤销与返回刚才位置应容易找到。连接设置、导出细分格式和高级 Beta 控制可以放到次级位置。

已有 `selectionBar` 定义了“聊这张”，但主界面实际采用 UIKit 的另一套工具栏。开发时要沿真实渲染路径接入，不能只修一个未被展示的 SwiftUI 组件。[E05、E12]

### 简单也需要解释

根部输入区域把短按打字、长按听写、松手提交藏在同一入口，而 Brief／实时 Beta 又在上方并列。它混合了输入方式与处理方式。[E04—E06]

建议普通状态清楚呈现文字输入和麦克风；“整理已有表达／展开想法”属于工作意图；实时流式成图属于高级交互。三者可以逐步分层，不必做三个常驻模式开关。

## 五、功能投入的取舍

### 本轮继续做

修复作品保存与恢复的语义；保留目标明确的连续对话；补足阅读状态和缩放层级；改善改稿结果反馈；统一点击区域与设计 token；让画布库能找到旧稿；保留来源与原始附件。

### 保留已有功能，暂缓增加复杂度

清单、表格、手绘、附件、分组与语义连线继续可用。实时语音 Beta 继续提供，但须完成真人真机中断验收后再考虑成为默认主入口。网页维持现有调查与改稿流程，暂不追求与手机功能一一对齐。

### 本轮不投入

新模板矩阵、更多白板对象、复杂格式编辑器、会议听录、多说话人识别、账户和多人协作、云同步、自动市场监测大屏、多 Agent 编排、自动发布投放、全套重命名换肤，以及以安装包大小为主要目标的优化。

这些方向并非被永久排除。它们各自需要出现明确重复需求，再重新评估开发顺序。

## 六、几个容易走偏的地方

**不要把当前 UI 的轻盈感等同于不断减少文字。** 按钮的动词、作用对象与保存状态，会减少猜测。可以减少装饰性说明，同时保留帮助决策的信息。

**不要把“有撤销”视为所有恢复路径都可靠。** 放下后隔天恢复，与立即撤销是不同任务；修改后离开编辑器，与明确保存是不同承诺。

**不要为了展示智能，让每句话都生成新卡。** 用户可能只想讨论一个问题、解释一条关系或修正一句话。产品需要显示这轮动作究竟是什么；“零新增、只修改”也可以是完整结果。

**不要让主线程整库保存立即引出架构大改。** 当前 `persist()` 同步编码全部画布，并已有部分延迟合并保存。其在大规模使用中的性能需要测量；现阶段先用数据规模与时序证明问题，再考虑拆分存储或后台编码。[E09]

## 七、下一轮怎样判断做对了

使用真实任务连续验证：打开已有稿、提交一段表达、阅读结果、选中卡或组改两轮、手动改字、撤销一次、放下再恢复、关闭重开、导出供自己阅读。

记录：是否反复找输入入口，是否重找刚才的对象，是否读不清正文，是否说不清 AI 改了哪里，是否丢失关系或手改，是否愿意继续使用同一份稿。

优先级由这些实际摩擦决定。功能数量、模型生成卡片数量、动画长度与截图是否饱满，都不应代替上述判断。
