# Brand Radar 第一版开发计划

更新日期：2026-08-31

## 交付目标

五个工作日内完成一个可由企划人员实际使用的默认场景：使用真实模型 API Key 读取咖啡品类 Replay / 公开材料，产出情报流、未来 30 天关键节点、关键词、三条 Brief 和本地 HTML 周会稿，并在后续交互入口中完成来源查看与人工采用、退回或补齐来源。

开发顺序以业务闭环为准。先让同一批材料经过真实 Agent 得到一份可复核结果，再做页面；页面不另写静态结论。

## 第一天：把业务样本准备成可工作的观察包（骨架已实现）

- 确定 2026 年 9 月 7 日至 13 日的瑞幸默认观察设置。
- 准备材料清单，补齐来源、日期、链接或文件位置、来源类型和版本关系。
- 至少包含一组重复材料、一组新旧版本、一项无关或过期内容、一项信息不完整的内容和一个风险节点。
- 人工先做一份期望结果，确认合并边界、优先级和三条 Brief 的证据关系。

完成标志：企划人员不看代码也能读懂观察包，并能指出每条期望结论来自哪里。

## 第二天：打通真实 API 的完整链路（已形成 Day 1–2 周会骨架）

- 增加 `brand_radar_weekly` 当前场景，只读取本次观察包。
- 增加“真实模型必需”开关；缺 Key、错误 Key或模型失败时明确停止。
- 跑通读取、版本核对、事件合并、优先级判断、日历、关键词和 Brief 生成。
- 默认停在人工复核前，不调用发送、发布、投放或预算工具。

完成标志：使用一个用户授权的测试 Key 跑出完整结果，三条 Brief 都引用存在的情报卡；更换一个关键词后结果发生合理变化。

阶段判定：Day 1–2 的观察包、单场景 CLI、专用校验、严格 API 开关、人工复核边界和本地 HTML 周会稿已实现。当前 `schema_version=1.1` 使用真实 DeepSeek `deepseek-v4-flash` 跑通默认周报，主演示为 `outputs/brand_radar_weekly-real-20260901-100927-543102.json` 与同名 HTML：27.6 秒，7 卡 / 3 Brief、3 个调查动作、首轮生成即通过、`awaiting_human_review`、`external_actions=[]`。此前 `004131` 作为旧证据保留。库迪目标变体也成功，路径转向库迪缺少的来源与快闪关联。错误 Key 0.7 秒退出码 3，未降级 Mock、未生成新产物。它证明 Day 1–2 可运行骨架成立，但 Brief 仍是企划雏形，来源包无图像素材或实时抓取，未来 30 天是关键节点而非逐日内容，因此不能称为完整成熟 Agent。

## 第三天：提升周会稿与复核体验

- 保持当前 `schema_version=1.1` 本地测试绿灯；当前测试数为 73。
- 用业务语言复核默认周报和库迪变体，确认 Brief 能进入企划会讨论而不是只满足 JSON 校验。
- 丰富来源包质量：优先补官方品牌、政府 / 活动、竞品公开页和可复查材料；图像素材只在来源和权限明确时进入。
- 把“未来 30 天关键节点”继续写成关键节点，不扩写成没有来源的逐日内容。
- 优化 HTML 周会稿的信息层级，让企划人员先看到“本周优先讨论 / 信息还不够，先别放进方案 / 明确不采用 / 继续观察”，再看来源，最后由人确认；不要再把一句模型摘要措辞当作整份周报失败。
- 继续验证关键词、竞品和矛盾材料变化时，调查路径与结果发生可解释变化。

完成标志：不仅能输出合规 JSON，还能展示一条可复查的“目标 → 计划 → 受限行动 → 反馈 → 调整 → 结果”链，并最终停在人工复核。

## 第四天：评估交互 Dashboard / chat

- 以当前 JSON + HTML 周会稿为基础，评估是否需要交互 Dashboard、GUI chat，或继续直接产出稳定周会稿。
- 展示观察设置、情报流、未来 30 天关键节点、重点关键词和三条 Brief。
- 支持按品牌、类型、优先级、日期和关键词筛选。
- 点击日历、关键词或 Brief 引用能定位对应卡片和来源。
- 提供采用、退回、补齐来源三种人工决定，只保存在本机本次会话。
- 显示真实模型 / Mock、Replay / 公开 / 人工材料的清楚标识。

完成标志：交互入口读取第二、三天生成的同一份结果，没有另一套写死的演示结论；如果周会稿已经足够，允许先不做复杂 Dashboard。

## 第五天：按真实业务走一遍

- 用默认观察包和真实模型跑一次周企划演示。
- 验证错误 Key、断网、缺材料、无效引用和来源打不开等失败路径。
- 从结果生成完成后计时，确认新用户能在三分钟内找到重点、查看依据并处理一条 Brief。
- 补充一张真实页面截图、最小启动说明和 Mac Mini 回读记录。
- 只有以上通过后，再决定是否迁移早期目录。

完成标志：PRD 的业务验收逐项有真实运行证据；仓库状态与 README 表述一致。

## 仓库整理顺序

当前先保持运行依赖稳定：

- 保留 `run.py`、`framework/`、`v3_agent/tools.py` 和 `scenarios/tools_real.py` 的现有位置。
- 新增当前 Brand Radar 场景、Replay 材料和本地 HTML 周会稿；交互 Dashboard / chat 作为下一阶段候选。
- README 只把新场景作为当前产品，把 V1-V3 和旧场景标为早期探索。
- 新入口通过后再做单独迁移提交；迁移时同时更新 import、命令和最小回归测试。

## 何时停止扩张

出现下列情况时回到本周唯一场景，不继续加设施：

- 为了多品牌、多 Agent 或实时抓取推迟真实 API 全流程。
- 页面开始产生与 Agent 输出无关的静态结果。
- 为了目录美观移动仍被执行器依赖的文件。
- 为了展示复杂度增加数据库、账号、调度、向量库或自动外发。
- 同一失败在依赖安装、构建或模型接入上重复两次仍没有新证据。
