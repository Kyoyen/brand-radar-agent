# Brand Radar Demo 开发计划

更新日期：2026-08-31

目标是尽快得到第一版可操作页面。默认采用静态 HTML/CSS/JavaScript + JSON Replay；只有当这一方案无法完成交互时才增加框架或后端。

## 第一步：让数据和页面出现

- 新建独立 `demo/` 目录。
- 准备一份瑞幸 / 咖啡品类 Replay JSON。
- 做出观察设置、情报流、日历、关键词和 Brief 的单页布局。
- 页面明确显示 `REPLAY`。

完成标志：通过一条本地命令能打开页面，并看到完整默认案例。

## 第二步：让页面真正可操作

- 支持编辑品牌、地区、竞品和关键词。
- 支持按品牌、事件类型和关键词筛选。
- 合并相同 `campaign_id` 的重复材料。
- 点击日历或关键词会更新情报流。
- Brief 建议跟随当前筛选结果变化，并引用卡片 ID。

完成标志：用户可以完整走完 PRD 的三分钟路径。

## 第三步：整理成可继续迭代的仓库

- 把早期 CLI 和 V1-V3 探索代码移入清晰的 `legacy/` 区域，保留 Git 历史。
- 删除失效入口、旧展示页和与当前 Demo 无关的说明。
- 补充最小启动说明和一张真实页面截图。
- 用少量自动检查验证 Replay 解析、去重和筛选。

完成标志：新用户打开仓库时首先看到可运行 Demo，不会把历史原型误认为当前产品。

## 技术取舍

- 优先：浏览器原生能力、本地 JSON、可读代码、零密钥启动。
- 可以：少量 Python 辅助脚本或一个轻量模型接口。
- 推迟：前后端分离、数据库、账号体系、任务调度、复杂 Agent 框架。

## 停止扩张条件

出现以下情况时回到最小页面，而不是继续加设施：

- 为了技术架构推迟可操作页面。
- 为了接入实时来源阻塞 Replay Demo。
- 为了视觉效果增加大量依赖。
- 为了展示 Agent 概念引入多个没有必要的角色或流程。
