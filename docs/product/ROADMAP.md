# Brand Radar 产品路线图

更新日期：2026-09-01

## 当前路线

先把已经真实跑通的品牌驱动骨架准确带回 GitHub `main`，重做仓库主页和真实 Demo 展示；随后继续补完整营销 Agent、修正问题并丰富图文回答。GUI 最后进入，重点是企划桌面式无限画布，六问只作为可跳过的首次使用弹窗。

```text
已完成的真实模型骨架
        ↓
GitHub main / 主页真实更新
        ↓
完整 Agent 结构 + 营销内容质量 + 问题修正
        ↓
可组合的图文回答
        ↓
左侧导航 + 右侧企划无限画布
        ↓
更丰富的来源、图像与日常使用能力
```

## 已完成基线

- 通用 `BRAND.md`、六问终端建档和本机定制档案。
- 信号筛选、品牌契合、Brief 转译三项营销技能。
- 真实模型 API 驱动的咖啡 Replay 周企划。
- 有界的“观察 → 选择技能 / 工具 → 反馈 → 再决定或成稿”循环。
- 情报卡、30 天关键节点、关键词、三条 Brief 和同源 HTML 周会稿。
- 专用结果校验、错误 Key 明确失败、原子保存和人工复核停止点。
- 真实 DeepSeek 主演示与 100 项测试。

这证明可运行骨架成立，但还缺少真实定制品牌对比、可回看的任务历史、人的采用 / 退回记录、页面视觉检查和面向普通营销人员的入口。

## 当前动作：更新 GitHub `main` 与项目主页

当前功能分支完整继承远端 `main`，因此只允许普通快进，不重写历史。

### `main` 整理

- 默认入口只指向当前 Brand Radar 主链；早期 V1–V3 和旧场景明确标为探索资产。
- 保留可复现的安装、可选品牌建档、真实运行和测试命令。
- 不提交本机品牌档案、原始运行输出、密钥、虚拟环境或带本机路径的材料。
- 公开前扫描已跟踪文件与截图，确认没有凭证、本机目录、Cookie 或私有结果。

### GitHub 主页

- 首屏用企划桌面概念图做主视觉，让陌生访客先感受到产品会怎样工作。
- 从一个真实企划工作瞬间切入，再展示情报便利贴、素材、日历和 Brief。
- 用咖啡周会稿作为第二个演示证据，说明当前已经能得到的结果。
- 品牌档案只作为可选设置轻量出现，不把六问写成主功能。
- 快速开始和数据安全放在后半段，避免首页像工程汇报；概念图仍需清楚标明尚未上线。
- 补充仓库 description、topics 和 social preview；许可证未确定前不擅自添加许可证。

完成表现：陌生访客在一分钟内能说清 Brand Radar 为谁解决什么问题、当前能不能跑、真实 Demo 在哪里，以及企划桌面仍是下一阶段。

## 第二轮：完整可用的营销 Agent

### 2.1 统一一条真实使用主链

目标是让企划人员从“我这周要回答什么”自然走到“我准备采用哪条 Brief”，而不是知道多个脚本参数。

- 保留一个当前产品入口，统一品牌档案、任务设置、材料、Agent 循环、结果和人工决定。
- 将一次运行明确表示为一个 Radar 任务：包含标题、品牌、业务问题、材料、状态、结果和时间。
- 允许从已有任务复制范围与材料，再作为新一周任务运行。
- Mock 继续只做程序检查；普通产品路径默认优先真实模型，并清楚显示当前模式。

完成表现：新使用者按一条说明即可完成品牌选择、任务创建、真实运行、查看结果和人工决定。

### 2.2 补齐 Agent 的记忆与知识

不先做复杂数据库，先把四类本地信息关系理顺：

| 信息 | 第一阶段保存方式 | 作用 |
|---|---|---|
| 品牌长期记忆 | 通用或本机 `BRAND.md` | 每次任务的品牌判断起点 |
| 当前工作记忆 | 本次 Radar 任务状态 | 保存范围、已读材料、工具反馈和当前缺口 |
| 营销知识 | Replay、人工材料和公开来源索引 | 为信号、卡片和 Brief 提供依据 |
| 历史记忆 | 已完成 artifact 与人工采用 / 退回记录 | 回看、复制和延续上次工作 |

- 人工采用、退回或补充来源的决定与本次结果一起保存。
- 人的单次决定不自动改写 `BRAND.md`；只有明确确认时才更新长期品牌记忆。
- 历史列表只读取完整任务；失败或中断任务显示失败状态，不伪装成成功结果。
- 后续真实需要多人共享、跨设备同步或大量检索时，再判断是否引入数据库或向量检索。

完成表现：关闭程序后仍能打开上次任务，知道 Agent 当时读了什么、为什么这样建议、使用者最后如何处理。

### 2.3 强化营销 Agent 的特色能力

- 让 `BRAND.md` 在每次调查选择、优先级和 Brief 成稿中都产生可解释影响。
- 保持小而清楚的技能目录；先把三项现有技能打磨出明显差异，再决定是否增加“Campaign 解构”“内容机会地图”或“人群场景提炼”。
- 支持材料变化后重新规划：更换品牌关键词、竞品或冲突材料时，调查路径与结果应合理变化。
- 把工具进度翻译成营销语言，例如“正在核对竞品版本”，而不是显示内部函数名。
- 改善三条 Brief 的差异度、品牌语气、创意触发点和可执行下一步。
- 结果卡同时回答：发生了什么、为什么值得进企划会、是否适合品牌、依据在哪里、还缺什么。
- 让结果能够表达文字、图片、视频预览、来源、时间节点和 Brief 等不同内容块；媒体必须保留来源与使用状态。
- Agent 选择对当前问题有帮助的内容块，不为“图文并茂”添加无关图片或视频。

完成表现：通用品牌档案与一份真实定制品牌档案运行同一观察包时，调查选择、优先级或 Brief 至少出现一种合理且可说明的差异。

### 2.4 第二轮问题修正清单

先修会破坏使用体验或主演示可信度的问题：

1. 完成定制品牌档案的真实 API 对比运行，排除品牌档案“已读取但不影响结果”的问题。
2. 检查中断、断网、材料缺失、无效来源和修正失败后是否残留误导性任务。
3. 在真实浏览器打开周会稿，修正卡片层级、长文本、窄窗口和来源展开的视觉问题。
4. 继续压低重复情报、相似 Brief、开发术语和缺少业务解释的内容。
5. 整理旧场景对当前入口造成的混淆；只在新入口稳定后移动目录或拆分依赖。
6. 确保任何日志、历史、截图和 Git 提交都不出现 API Key 或本机隐私路径。

完成表现：真实主演示、错误 Key、断网 / 中断和品牌对比都有清楚结果；企划人员看到的是业务过程，不需要读终端日志判断成功与否。

## 第三轮：企划桌面 GUI

GUI 不改变 Agent 逻辑，也不另存一套结果。它复用品牌六问状态机、任务状态、历史 artifact 和同源 JSON。

### 3.1 基础外壳与品牌弹窗

- 首次打开显示普通品牌建档弹窗；关闭、跳过或不填写时使用通用 `BRAND.md`。
- 六问逐题显示，支持回答、跳过、返回和最终确认；后续可从“品牌档案”重新打开。
- 左侧导航固定包含新建、历史、品牌档案和设置。
- 设置只显示 Provider、模型和 Key 是否配置，不回显 Key 内容。

完成表现：使用者可以直接关闭弹窗开始工作；品牌建档有帮助但不抢占产品主流程。

### 3.2 右侧企划无限画布

右侧像企划人员自己的办公桌面，可以缩放、拖动、分组和聚焦：

- 情报便利贴：轻微倾斜、分色和弹性入场，但内容位置保持可预测。
- 来源与媒体：图片、视频预览、网页来源和人工摘录都以独立对象出现。
- 企划组件：竞品对比、关键词簇、30 天节点、Brief 和人的采用 / 退回决定可以并排组织。
- Frame：Agent 先把对象放进“本周重点、待核、竞品、日历、Brief”等有限分区，使用者再自由调整。
- Chat：输入框和当前 Agent 状态不遮挡画布，追问产生新对象或更新已有对象。

完成表现：企划人员既能自由摆放内容，也能一键回到当前重点，不会在无限空间里迷路。

### 3.3 实用性、动效与性能

- 情报卡固定呈现状态、事实、品牌意义、建议、来源和人工操作。
- Brief 卡突出人群、时机、创意逻辑、引用情报和下一步。
- 来源允许展开，但不让 URL 和技术字段占据主阅读路径。
- 有合法图片时显示事件或 Campaign 图片及来源；视频默认只显示封面和链接，不自动播放。
- 仅渲染当前视口和邻近对象，大图使用缩略图，离屏媒体延迟加载。
- 提供缩放到全部、回到重点、搜索、状态筛选和一键整理。
- 动效只用于对象进入、拖动、聚焦和状态变化；支持“减少动态效果”，禁止持续晃动和无意义装饰动画。
- 采用 Apple 式清晰层级和克制材质，并吸收 Cowart 的无限画布与媒体占位思路，不复刻任何现有产品界面。

完成表现：新用户能在结果生成后三分钟内找到重点、打开依据并处理一条 Brief。

### 3.4 GUI 主演示与主页更新

- 用真实 Key 从 GUI 跑通一次完整咖啡周企划。
- 错误 Key、缺材料和中断在界面中明确失败，不出现伪成功卡片。
- 截取真实品牌建档、Agent 工作和结果页面，替换 GitHub 主页中的过渡截图。
- 记录一条从建档到人工决定的短演示素材。

完成表现：GitHub 主页、实际 GUI 和后端结果三者描述同一套真实产品。

## 后续方向：来源与日常营销工作

这些能力不阻塞第二、三轮，但每次迭代都要继续观察营销人员真正缺什么材料：

- 在权限和来源清楚的前提下连接更多公开网站、用户上传文件和图片。
- 为来源建立候选、实际使用、冲突和失效状态，避免“抓得多”等于“判断好”。
- 根据真实使用判断是否需要自动刷新、团队共享、数据库、账号系统或多 Agent。
- 只有在一个明确营销工作无法由当前单 Agent 完成时，才增加新的角色或复杂设施。
