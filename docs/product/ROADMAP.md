# Brand Radar Product Roadmap

更新日期：2026-08-31  
状态：产品迭代计划

## 1. Roadmap Boundary

本计划描述产品能力如何从当前多场景 POC 迭代成最小可用的营销情报 Dashboard。仓库执行、Mac Mini 接力和作品集表达分别见 `../AGENT-EXECUTION-GOAL.md`、`../handoff/2026-08-31-macmini-bootstrap.md` 和 `../PORTFOLIO-EVIDENCE.md`。

## 2. Product Cut

| 切线 | 包含阶段 | 用户获得什么 |
| --- | --- | --- |
| 最小闭环 | P0-P1 | 一个能配置、聚合、筛选、看证据并给 Brief 角度的瑞幸情报流 |
| MVP | P0-P2 | 包含情报流、营销日历、新兴关键词和 Brief 建议的营销 Dashboard |
| Agent 质量增强 | P3 | 可版本化、可回放、可换模型的营销 Agent 壳 |
| 日常使用增强 | P4 | 稳定接入公开来源并吸收用户反馈的工作台 |

## 3. P0: 锁定瑞幸 Replay 案例

产品结果：所有设计、数据和 Agent 行为围绕同一个案例对齐。

交付：

- `BrandProfile`：瑞幸咖啡、现制咖啡品类、全国 + 上海、过去 7 天 + 未来 30 天。
- 竞品候选与确认流程：候选依据可见，确认后才进入监测。
- 固定 Replay 材料，覆盖竞品 Campaign、节日、地区活动、突发热点、新兴关键词和敏感纪念日。
- `SourceDocument -> MarketingSignal -> SignalCluster -> BriefSuggestion` 字段与引用关系。
- 营销 Agent 角色、筛选规则、输出顺序、禁用口吻和第一个 System Prompt 版本。
- Dashboard 线框与营销编辑部视觉基调。

验收：

- 任何一条需求都能落到瑞幸标准演示路径中的一个页面、动作或输出。
- 固定材料足以制造重复报道、无关高热、单源待核和敏感节点四类 bad case。
- 产品文案不出现 KFC 专属称呼，也不把简历展示当作产品目标。

## 4. P1: 让统一情报流转起来

产品结果：用户配置观察面、确认竞品并刷新后，看到经过 Agent 主动筛选的统一营销情报流。

能力：

- 品牌、品类、地区、时间窗口和关注方向输入。
- 竞品候选、候选理由和用户确认。
- Replay 信号进入统一标准，完成去重、聚类、相关性判断和排序。
- 主 Dashboard 展示 5-10 个情报簇，而不是原始链接列表。
- 情报卡片展示 Agent 判断、`why_now`、标签、证据、置信度和待核项。
- 品牌、地区、事件类型、节点、风险和时间筛选。
- `关注 / 忽略 / 查看证据 / 生成 Brief` 基础动作。

阶段出口：瑞幸 Replay 案例能够完成 `确认观察面 -> 刷新 -> 找到优先信号 -> 打开证据 -> 生成一个 Brief 角度`。

## 5. P2: 补齐营销 Dashboard

产品结果：把可运行的情报流变成营销企划每天愿意打开的工作面板。

营销日历：

- 未来 30 天展示节日、消费节点、地区活动、品牌动作和敏感纪念日。
- 点击节点后过滤情报流，并提示合理准备窗口。
- 敏感日期使用克制风险标签，高风险冲突默认暂停相关促销 Brief。

新兴关键词：

- 展示至少 10 个近期新出现、增速明显或跨来源共现的词。
- 词的大小、颜色和风险标记有明确含义。
- 点击后同步过滤情报流，并展示出现原因和关联来源。

Brief 建议：

- 根据当前观察面给出 3 个优先角度。
- 每个角度包含机会命题、why now、证据、可执行方向、风险和未知。
- 生成内容引用现有 Signal / Cluster，不脱离证据自由发挥。

MVP 出口：

- 标准演示全程不超过 3 分钟。
- Replay 无密钥可运行，Live / Replay 不混淆。
- 情报流、日历、关键词和 Brief 四个区域由同一观察面与同一证据链驱动。
- 用户更换地区、关键词或竞品名单后，无需改代码即可得到新的筛选结果。

## 6. P3: 精修营销 Agent 壳

产品结果：Agent 的营销判断和表达可被持续调整、回放和比较；更换模型不会破坏产品行为契约。

能力：

- System Prompt、工具说明、排序规则和输出 Schema 版本化。
- 建立 bad-case 集：重复聚类失败、竞品误判、热点误升权、事实与推断混淆、敏感日期表达不当、Brief 无证据。
- 每次修改只改变一个可说明的规则，并对固定瑞幸案例做 Replay 对照。
- 模型接入通过统一 Adapter；产品可连接用户自己的模型。
- 前端显示的判断、标签和证据直接来自结构化输出。

验收：

- 同一 Replay 输入可以比较相邻 Prompt 或规则版本的输出差异。
- Agent 失败能定位到来源、工具、过滤、Prompt、Schema 或渲染中的一层。
- 版本不通过 bad-case 回归时可以回退。

## 7. P4: 扩展真实来源与日常使用

产品结果：在不破坏 Replay 稳定性的前提下，让产品逐步处理当天真实的公开营销信号。

方向：

- 接入稳定、合法的品牌公开页、营销媒体、官方活动 / 节点和政策来源。
- 用户提供公开小红书 / 抖音 URL 或授权数据时进入同一标准化链路。
- 增加刷新状态、部分失败、来源缺失和最后成功时间。
- 根据 `关注 / 忽略 / Brief` 反馈调整排序，保留可解释变化。
- Live 数据量、覆盖率和时效以真实运行记录评估，不用 Replay 数字冒充。

验收：

- 至少一个公开来源完成真实刷新，并清楚显示来源和时间。
- 来源失败不会静默生成完整结论，也不会把 Replay 填充为 Live。
- 用户反馈在下一次排序中产生可见、可解释的变化。
