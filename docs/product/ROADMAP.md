# Brand Radar 第一版开发计划

更新日期：2026-08-31

## 交付目标

五个工作日内完成一个可由企划人员实际验收的默认场景：使用真实模型 API Key 读取咖啡品类 Replay / 公开材料，产出情报流、30 天日历、关键词和三条 Brief，并在 Dashboard 中完成来源查看与人工采用、退回或补证。

开发顺序以业务闭环为准。先让同一批材料经过真实 Agent 得到一份可复核结果，再做页面；页面不另写静态结论。

## 第一天：把业务样本准备成可工作的观察包

- 确定 2026 年 9 月 7 日至 13 日的瑞幸默认观察设置。
- 准备材料清单，补齐来源、日期、链接或文件位置、来源类型和版本关系。
- 至少包含一组重复材料、一组新旧版本、一项无关或过期内容、一项待核内容和一个风险节点。
- 人工先做一份期望结果，确认合并边界、优先级和三条 Brief 的证据关系。

完成标志：企划人员不看代码也能读懂观察包，并能指出每条期望结论来自哪里。

## 第二天：打通真实 API 的完整 Agent 流程

- 增加 `brand_radar_weekly` 当前场景，只读取本次观察包。
- 增加“真实模型必需”开关；缺 Key、错误 Key或模型失败时明确停止。
- 跑通读取、版本核对、事件合并、优先级判断、日历、关键词和 Brief 生成。
- 默认停在人工复核前，不调用发送、发布、投放或预算工具。

完成标志：使用一个用户授权的测试 Key 跑出完整结果，三条 Brief 都引用存在的情报卡；更换一个关键词后结果发生合理变化。

## 第三天：让结果可以复核

- 增加 Brand Radar 专用结果校验。
- 检查来源存在、卡片 ID 唯一、Brief 引用有效、来源类型明确和待核原因完整。
- 保存本次读取成功、失败、排除、版本取舍和合并记录。
- 处理材料缺失、版本冲突、可能重复和三条 Brief 过于相似的情况。

完成标志：企划人员能从任一 Brief 回到卡片和原始材料；Agent 不会把缺证据内容写成确定事实。

## 第四天：接到一个轻量 Dashboard

- 展示观察设置、情报流、30 天日历、重点关键词和三条 Brief。
- 支持按品牌、类型、优先级、日期和关键词筛选。
- 点击日历、关键词或 Brief 引用能定位对应卡片和来源。
- 提供采用、退回、补证三种人工决定，只保存在本机本次会话。
- 显示真实模型 / Mock、Replay / 公开 / 人工材料的清楚标识。

完成标志：页面读取第二、三天生成的同一份结果，没有另一套写死的演示结论。

## 第五天：按真实业务走一遍

- 用默认观察包和真实模型跑一次周企划演示。
- 验证错误 Key、断网、缺材料、无效引用和来源打不开等失败路径。
- 从结果生成完成后计时，确认新用户能在三分钟内找到重点、查看依据并处理一条 Brief。
- 补充一张真实页面截图、最小启动说明和 Mac Mini 回读记录。
- 只有以上通过后，再决定是否迁移早期目录。

完成标志：PRD 的业务验收逐项有真实运行证据；仓库状态与 README 表述一致。

## 仓库整理顺序

当前先保持运行依赖稳定：

- 保留 `run.py`、`framework/`、`v3_agent/tools.py` 和 `scenarios/tools_real.py` 的现有位置。
- 新增当前 Brand Radar 场景、Replay 材料和 Dashboard 入口。
- README 只把新场景作为当前产品，把 V1-V3 和旧场景标为早期探索。
- 新入口通过后再做单独迁移提交；迁移时同时更新 import、命令和最小回归测试。

## 何时停止扩张

出现下列情况时回到本周唯一场景，不继续加设施：

- 为了多品牌、多 Agent 或实时抓取推迟真实 API 全流程。
- 页面开始产生与 Agent 输出无关的静态结果。
- 为了目录美观移动仍被执行器依赖的文件。
- 为了展示复杂度增加数据库、账号、调度、向量库或自动外发。
- 同一失败在依赖安装、构建或模型接入上重复两次仍没有新证据。
