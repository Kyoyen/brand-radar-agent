# Brand Radar 营销企划 Agent PRD

更新日期：2026-09-01

## 核心判断

第一版要交付的不是一个静态情报看板，而是一名企划人员可以实际使用的完整工作流程：输入下周业务问题，接入真实模型 API Key，让 Agent 读取可复查的材料，完成版本核对、事件合并、优先级判断和 Brief 草拟，最后由企划人员查看来源并作决定。

Replay 保证输入稳定，真实模型完成判断与生成。两者共同构成第一版的业务验收。无 Key 的 Mock 运行只用于确认程序没有断，不代表 Agent 已经完成真实工作。

产品优先级按这个顺序执行：用户使用 > 产品功能 > 快速成型 > 过程可复现。安全、来源约束和不外发是基础门槛，不作为卖点包装；第一版真正要证明的是它能围绕营销目标调查、在受限动作里取证、根据反馈调整判断，并稳定产出营销企划可读的交付物。

## 下一轮产品方向（待确认）

下一轮不直接从 CLI 跳到一个漂亮但空心的界面。先把现有骨架补成一套可以连续使用的单 Agent：它知道自己服务哪个品牌，记得本次任务与人的取舍，能读取营销材料和知识，能按需要选择技能与工具，能在反馈后继续判断，并把每次结果保存为可回看的工作记录。完成这一步后，再给它增加轻量 GUI；GitHub `main` 与仓库主页也只展示已经真实跑通的能力。

推荐顺序如下：

| 顺序 | 产品结果 | 为什么先做 |
|---|---|---|
| 1. 完整 Agent 主链 | 品牌记忆、任务记忆、营销知识、技能、工具、反馈循环和稳定成果成为一体 | 确保界面背后真有一名能工作的营销 Agent |
| 2. 修正现有问题 | 用通用与定制品牌各跑一次，修正内容、失败提示、历史记录和页面展示问题 | 让主演示稳定，不用界面掩盖问题 |
| 3. 整理 `main` 与 GitHub 主页 | 默认分支呈现真实愿景、特色、演示截图、能力和启动方法 | 让第一次看到仓库的人理解项目价值并能复现 |
| 4. 轻量 GUI | 先做品牌六问，再做带新建、历史、品牌档案和设置的左右分栏工作台 | 界面复用已经跑通的后端，而不是另造一套 Demo |
| 5. 丰富来源与图文结果 | 在来源许可清楚的前提下增加图片、更多公开材料和更好的聚合展示 | 提升企划启发，不把装饰当成证据 |

这份 PRD 和 Roadmap 是本轮唯一改动。未获得方向确认前，不开始 Agent、GUI、`main` 合并或 GitHub 主页制作。

## 一名完整 Brand Radar Agent 由什么组成

Brand Radar 不把“记忆、知识库、工具和 Prompt”当成互相孤立的功能。它们共同服务同一条营销工作：从品牌出发，把零散信号变成企划人员可以判断和采用的方向。

| 组成 | 在 Brand Radar 里的含义 | 企划人员获得什么 |
|---|---|---|
| 品牌记忆 | `BRAND.md` 保存品牌希望被怎样记住、核心人群、承诺、语气、热点取舍和红线 | 每次工作先按品牌判断，不从一张空白聊天框重新解释品牌 |
| 本次工作记忆 | 保存业务问题、时间、地区、竞品、已读材料、调查反馈和当前缺口 | Agent 不会每轮忘掉刚才看过什么，也不会重复调查 |
| 营销知识 | Replay、用户材料和未来经过许可的公开来源按来源、日期、版本和使用状态组织 | 能区分“可参考材料”和“足以支撑建议的事实” |
| 运行规则 | `agent/AGENTS.md` 固定营销思考方式、品牌优先和人工控制点 | 不同模型仍沿着同一套营销工作方法行动 |
| 营销技能 | 信号筛选、品牌契合、Brief 转译等可按需要调用的专门能力 | Agent 不是每轮使用同一个大 Prompt，而是选择当前最需要的能力 |
| 调查工具 | 读取本地材料、比较版本、对比竞品和核对冲突；未来再增加经过许可的公开来源连接 | Agent 能通过行动补充判断，而不是只凭语言猜测 |
| 有界循环 | 目标 → 观察 → 选择技能 / 工具 → 读取反馈 → 再决定或成稿 | 调查路径会随材料变化，但不会无限运行 |
| 成果与历史 | 每次生成同源 JSON、可读情报卡和运行摘要；人工采用、退回或补充来源的决定与本次任务相连 | 可以回看“当时为什么这样判断”，并从历史任务继续工作 |

这里的“记忆”分三层：`BRAND.md` 是长期品牌记忆；一次任务里的材料和反馈是工作记忆；已完成结果与人的决定是历史记忆。人的一次采用或退回不会自动改写品牌原则，只有使用者明确确认时才更新 `BRAND.md`。第一阶段先使用本地文件保存，不为了“拥有记忆”预先引入数据库。

## 营销特化的产品亮点

- 先建立品牌，再开始调查：`BRAND.md` 不是附加设置，而是 Agent 的判断起点。
- 不把热度当机会：每条信号都要经过来源可信度、时间窗口、品牌契合与可行动性判断。
- 不只给结论：情报卡同时呈现“发生了什么、为什么值得进企划会、依据在哪里、还缺什么”。
- 不把所有材料都塞进最终稿：Agent 可以主动排除过期、重复、冲突和与本次目标无关的信息。
- 不只生成一种创意：三条 Brief 分别从不同人群、场景、时机或竞品空位出发，避免换标题式重复。
- 不隐藏成稿过程：界面展示每轮选择、工具反馈和下一步理由的业务摘要，但不暴露模型私密推理文本。
- 不替人做最后决定：人的采用、退回和补充来源结果会进入历史，外发与投放仍由人决定。

## 完整使用旅程

1. 首次打开时，使用者选择“快速使用通用品牌”或进入六问品牌建档。
2. Agent 显示当前生效的品牌档案，让使用者知道它会依据什么工作。
3. 使用者新建一次 Radar，说明这周要回答的问题、品牌、地区、竞品和时间。
4. 使用者选择 Replay、上传材料或补充公开链接；系统清楚显示来源状态。
5. Agent 逐轮观察、选择营销技能和调查动作，并把简洁进度显示给使用者。
6. 结果以情报卡、关键节点、关键词和三条 Brief 呈现；每项都可展开来源。
7. 使用者对 Brief 选择采用、退回或补充材料，并写一句原因。
8. 本次工作进入历史，可以再次打开、复制为新任务或在补充材料后重跑。
9. 只有使用者主动确认时，某项长期品牌取舍才写回 `BRAND.md`。

## 轻量 GUI 方向

GUI 是已经跑通的 Agent 的使用入口，不是新的事实源。它继续读取同一品牌档案、任务状态、调查结果和最终 artifact。

### 第一步：品牌建档画面

- 欢迎页用一张简洁品牌卡说明：建档能让 Agent 更像品牌自己的企划搭档。
- 同时提供“开始六问”和“先用通用模式”两个同等清楚的入口，不强迫建档。
- 六问一次只显示一问，支持回答、跳过、返回修改和保存退出，并显示轻量进度。
- 问题旁给一条具体示例，帮助企划人员快速回答，不写成长表单说明。
- 完成后生成一张可阅读的品牌摘要卡；使用者确认后才保存，后续可在主界面更新。

### 第二步：左右分栏工作台

左侧保持稳定导航，包含“新建 Radar、历史、品牌档案、设置”；右侧是当前工作的主画布。

- 新建：从一句业务问题开始，随后补充范围与材料；不是先填复杂配置表。
- 进行中：以 chat 式交流承接追问，同时把调查动作和反馈渲染成可展开的小卡片。
- 结果：在同一画布中按情报卡、30 天节点、关键词和 Brief 分组，不跳到另一套 Dashboard。
- 历史：按任务标题、品牌、日期、状态和使用模型显示过去工作，打开后可查看原结果或复制重跑。
- 品牌档案：查看当前 `BRAND.md` 摘要、回答覆盖情况和更新时间，支持重新进入六问。
- 设置：只显示 Provider、模型、API Key 是否已配置、默认材料位置和显示偏好；永不回显 Key 内容。

### 视觉语言

- 借鉴 Apple 设计中“层级、和谐、一致”的原则：重要内容优先、控件和内容层分明、窗口大小变化时仍能自然使用。
- 使用克制的浅色背景、圆角卡片、轻材质层次、系统字体和少量品牌强调色；避免大面积渐变、发光边框和仪表盘式堆砌。
- 卡片是信息单位，不只是装饰：状态、结论、理由、来源和人的操作在固定位置出现。
- 图片只在能帮助识别事件、Campaign 或内容风格时出现；必须保留图片来源与使用权限。没有合适图片时使用高质量文字卡，不用无关图库图填空。
- 桌面宽屏默认显示侧边栏，窄窗口可收起；导航层级不超过两层。

## GitHub `main` 与对外主页

当前 GitHub `main` 仍把产品描述为“品类情报看板”，并声称无 API Key 也能稳定演示、Dashboard 尚未完成，这已经落后于当前真实分支。下一轮要在 Agent 主链稳定后，通过普通合并把真实成果带回 `main`，不直接在默认分支上边试边改。

README 主页承担演示宣传目的，推荐采用以下叙事顺序：

1. 首屏：项目名、一句话愿景、真实产品画面和一个明确的本地运行入口。
2. 痛点：营销人员为什么会被零散来源、重复新闻、版本冲突和品牌不适配拖慢。
3. 工作方式：用一张简洁流程图说明“品牌 → 观察 → 调查 → 企划卡片 → 人工决定”。
4. 独特能力：突出 `BRAND.md`、营销技能、反馈循环、来源约束和三条差异化 Brief。
5. 真实演示：展示咖啡 Replay 的实际情报卡与周会稿截图，明确 Replay 与真实模型的区别。
6. 快速开始：品牌建档、真实周企划与错误 Key 行为三条最短命令。
7. 当前能力与下一步：用表格分清“已完成 / 正在做 / 后续考虑”，不宣传尚未实现的 GUI 或实时监测。
8. 项目信息：补充仓库 description、topics、social preview、许可证状态和贡献方式。

主页中的 hero、流程图、能力卡和截图使用统一视觉语言。宣传插画可以原创生成，但不得冒充产品截图；产品截图必须来自真实运行界面。第一轮 `main` 整理可以先使用当前真实 HTML 周会稿，GUI 跑通后再替换成新的实际界面截图。

## 下一轮成功标准

- 使用通用品牌档案和一份真实定制品牌档案分别运行时，Agent 的调查选择、优先级或 Brief 至少出现一种可解释差异。
- 新任务从品牌、问题和材料开始，结束于可保存、可回看、可复制重跑的本地历史记录。
- 中断、错误 Key、材料缺失和结果校验失败不会在历史中伪装成成功任务。
- 企划人员不用看终端日志，就能理解 Agent 正在读什么、为什么继续调查以及结果依据在哪里。
- `main` 上的一条真实启动命令能够复现默认 Demo；GitHub 首页只宣传当前已经跑通的功能。
- GUI 开发只有在上述 Agent 主链与主要问题修正后才开始；GUI 仍读取同一份品牌档案与结果，不产生平行逻辑。

## 谁在什么情况下使用

主要使用者是品牌方或代理公司的营销企划人员。典型使用时点是周企划会前 1 至 2 天，面对散落在新闻、活动日历、竞品资料、公开网页和内部摘录中的信息，需要回答：

> 下周有哪些信号值得跟进，哪些需要继续观察，哪些可能触发品牌或时间风险？

第一版默认场景：2026 年 9 月 4 日企划会前，为 9 月 7 日至 13 日准备瑞幸咖啡 / 现制咖啡 / 全国 + 上海的周度观察。默认竞品为星巴克中国、库迪咖啡、Manner 和麦咖啡。

## 本次工作需要什么材料

企划人员开始任务前确认：

- 本次使用通用 `BRAND.md`，还是通过六个可跳过的问题补充本机品牌档案。
- 品牌、品类、地区、竞品和关注关键词。
- 本周要回答的业务问题和准备覆盖的时间范围。
- 仓库内置 Replay 材料包。
- 使用者补充的公开网页、活动日历、竞品动作或研究摘录。
- 已知敏感日期、品牌安全要求和不应触碰的主题。

每份材料都要保留来源名称、材料日期、原始链接或文件位置，以及 `REPLAY`、`PUBLIC`、`MANUAL` 中的一种来源类型。没有来源的信息可以进入“信息不完整”区，不能进入已确认事实。

## 实际业务流程

| 环节 | Agent 完成的工作 | 企划人员看到或决定什么 |
|---|---|---|
| 1. 确认品牌与任务 | 读取通用或本机定制品牌档案，复述品牌、竞品、地区、时间和业务问题；发现缺项时列为待补充 | 完成或跳过品牌六问，确认本次观察范围，避免结果偏题 |
| 2. 阅读材料 | 逐份读取本次材料包，识别时间、品牌、事件、地区、来源和版本 | 能看到 Agent 实际读取了哪些材料 |
| 3. 核对有效版本 | 找到最新有效要求，排除已撤回、过期、重复、上一轮残留或无关信息 | 对版本冲突和来源不足作人工判断 |
| 4. 合并营销事件 | 把同一 Campaign 或同一节点的多条材料并为一张主卡，多个来源附在卡片下 | 不再被转载数量误导，可展开查看所有依据 |
| 5. 逐轮判断 | 每轮选择信号筛选、品牌契合或 Brief 转译，并决定执行一个本地查证还是根据已有反馈开始成稿 | 看到 Agent 为什么继续调查或停止，并调整不合业务常识的判断 |
| 6. 形成企划结果 | 生成情报流、30 天日历、重点关键词和 3 条 Brief 角度 | 查看每条 Brief 为什么值得讨论、引用了哪些卡片 |
| 7. 人工复核 | 暂停所有外发动作，列出风险和还缺的信息 | 采用、退回或要求补齐来源；决定是否进入正式 Brief 或后续执行 |

具体操作节奏和异常处理见 [下周营销企划工作流](../business/NEXT-WEEK-WORKFLOW.md)。

## 业务判断规则

### 优先级

- 本周跟进：与品牌和时间窗口高度相关，有清楚来源，并且本周可以形成企划动作。
- 继续观察：方向相关，但时间尚早、信号较弱或仍缺一项关键证据。
- 主动避开：存在敏感日期、品牌安全、错误联想、竞品高度占位或执行冲突。
- 信息不完整：来源、版本、日期或关键事实不够，暂时不能写成确定结论。

### 必须遵守的例外

- 同一材料出现多个版本时，以最新明确有效的指令为准，并保留被替换版本的说明。
- 草稿、转述和历史总结都不是自动真值；若与原始材料冲突，以原始材料和最新有效确认优先。
- 转载数量不等于重要性。同一事件合并后再判断，不用声量堆叠制造紧迫感。
- Brief 只能引用本次情报流中存在的卡片；没有卡片支撑的角度直接退回。
- 品牌安全、敏感日期、法律判断、对外发布、投放和预算动作必须由人确认。

## 交付结果

交付结果以校验通过后原子保存的 JSON 为准。JSON 中的 `executive_summary` 与 HTML 首页共用一份由已校验情报卡 priority 生成的人话结论，不保存无卡片支撑的模型草稿句；模型的实质判断仍可从卡片、Brief、逐轮选择和本地反馈追溯。CLI 会同步生成一份本地 HTML 周会稿，用来快速阅读品牌起点、本次实际使用的营销能力、Agent 每轮为什么继续或停止、本周重点、三条 Brief、未来 30 天关键节点、关键词、来源和人工复核项。首页稳定生成“本周优先讨论 / 信息还不够，先别放进方案 / 明确不采用 / 继续观察”的人话结论，并优先露出信息不完整的卡片。未来 GUI、chat 或 Dashboard 可以用于建档、解释、追问、追加材料和人工复核，但都必须读取同一份 JSON，不能成为唯一事实源或复制另一套静态结论。

来源在结果中分为三种状态：

- 候选来源：观察包或人工输入中出现，但尚未被本次判断引用。
- 实际使用来源：进入情报卡、日历、关键词或 Brief 的来源，必须保留 `source_id`、日期、类型和原始位置。
- 有冲突、需确认的来源：与当前版本、同事件材料或人工便签存在冲突，只能支撑“信息不完整”或风险提醒，不能写成确定事实。

### 情报流

一张卡代表一个营销事件，包含：事件标题、简要事实、涉及品牌、日期、地区、事件类型、为什么值得看、处理建议、风险或信息不完整的原因，以及全部来源。

### 营销日历

覆盖未来 30 天的关键节点，显示消费节点、地区活动、竞品动作窗口、准备截止日和敏感日期。第一版不是逐日内容日历；每个节点都要能回到对应情报卡。

### 重点关键词

展示本次材料中高频或新出现的词，并说明它来自哪些卡片。关键词用于发现主题，不单独充当结论。

### 三条 Brief 角度

每条包含：机会或问题、为什么是现在、目标人群或场景、关联情报卡、下一步建议、风险提醒和还缺的来源或事实。三条角度应有差异，不能只是同一主题换标题。

### 运行记录

保留本次任务范围、读取材料、版本取舍、合并结果、优先级理由、最终输出和失败原因。记录用于复核本次工作，不在第一版扩展成复杂评测平台。

## 第一版必须完成

- 可通过本机环境配置真实模型 API Key，并依次通过“真能跑”和“真像营销 Agent”两道硬门。
- API Key 无效、网络失败或模型返回异常时明确告知原因，不能静默改用 Mock 后继续伪装成真实结果。
- 提供一套来源、日期和类型齐全的 Replay 材料包。
- 允许编辑品牌、品类、地区、竞品、关键词、观察时间和业务问题。
- 生成情报流、30 天日历、重点关键词和 3 条 Brief 角度。
- 每个事实和 Brief 都能回到本次材料或情报卡；来源不足时显示“信息不完整，先别放进方案”。
- 默认停在人工复核前，不自动发送、发布、投放或改预算。

下一轮交互原则：GUI 只有在完整 Agent 主链与主要问题修正后才进入；它必须读取 CLI 与 HTML 已使用的同一份品牌档案、任务状态和 JSON，不能另写一套静态结论。

## 两道硬门

### 硬门一：真能跑

- 一条命令使用真实 Key 端到端成功；错误 Key 明确失败，不能降级 Mock。
- 结果原子保存，可复查来源、版本取舍、合并记录和模型运行信息；中断或校验失败不留下半成品。
- 默认只产生本机待复核结果，不发送飞书、不发布、不投放、不改预算。

当前 `schema_version=1.2` 已通过这道硬门：真实 DeepSeek `deepseek-v4-flash` 默认周报约 29.5 秒端到端成功，使用通用 `BRAND.md`，完成四轮决策与三个本地调查动作，产出 `outputs/brand_radar_weekly-real-20260901-115850-982265.json` 与同源 HTML、7 卡 / 3 条不同 Brief，最终为 `awaiting_human_review` 且没有外部动作；错误 Key 约 0.9 秒以退出码 3 明确失败，未新增 JSON / HTML / tmp，也未降级 Mock。

### 硬门二：真像营销 Agent

- 先加载实际生效的通用或本机定制 `BRAND.md`，再以营销目标驱动观察材料与当前缺口。
- 每轮只选择信号筛选、品牌契合或 Brief 转译中的一项能力，并决定执行一个受限本地查证或根据已有反馈开始成稿。
- 每次本地查证后读取反馈，再决定继续调查还是停止并生成；不能用一次性计划代替逐轮选择。
- 识别过期、重复、冲突和信息不完整的材料，并解释信号为什么值得进入企划会。
- 产出有来源约束的情报卡、30 天日历、关键词和 3 条不同视角 Brief。
- 关键词、竞品或矛盾材料变化时，调查路径与结果应合理变化，不能只是替换文案或返回固定 JSON。
- 专用校验失败时，只允许把结构化错误反馈给模型修正一次；再次失败就明确停止，不无限循环。
- 最终仍停在人工复核。

当前工作树已经实现最小的“BRAND 起点 → 目标 → 观察 → 选择一项营销能力与一个受限动作 → 读取反馈 → 继续或成稿 → 专用校验 → 最多一次修正 → 人工复核”闭环。当前品牌驱动主演示使用通用 `BRAND.md`，前三轮依次核对待核的上海咖啡快闪、上海旅游节版本组和当前旅游节来源，第四轮选择开始成稿；实际使用信号筛选与 Brief 转译，最终得到 7 卡 / 3 条不同 Brief。此前库迪目标变体只作为旧流程的历史兼容证据，不再承担当前品牌驱动主证据。它可以称为可运行的单 Agent 演示骨架，但 Brief 仍是企划雏形，来源包没有图像素材或实时抓取，未来 30 天只是关键节点，因此不能称为完整成熟或自治营销产品。

## 业务验收

一次有效验收应使用专门的测试 Key 或用户本机已有 Key，完成以下过程：

1. 启动任务后，页面或终端明确显示正在使用真实模型与 Replay / 公开材料。
2. Agent 读取完整材料包，能识别至少一组重复事件、一项版本取舍和一项信息不完整的内容。
3. 输出四类企划结果，每条卡片保留来源；三条 Brief 都引用存在的卡片。
4. 企划人员能在三分钟内完成“找到重点 → 查看依据 → 采用、退回或要求补齐一条 Brief 的来源”。三分钟从结果生成完成后开始计算，不把模型等待时间藏进操作时间。
5. 更换一个竞品或关键词后，结果随输入变化，不返回预先写死的同一套结论。
6. 填错 API Key 后必须明确失败且不降级 Mock；只有未使用 `--require-api` 且本机确实缺 Key 时，才允许主动进入已标记的 Mock 烟雾测试。
7. 日志、页面、提交记录和交接文件中不出现 API Key 明文。

当前 CLI 已生成本地 HTML 周会稿，但尚无 GUI chat、交互 Dashboard、自动刷新或实时抓取能力；这些不是 Day 1–2 的验收项。内容相关问题需要继续探索公开信息源，但新增来源必须进入观察包或人工补充材料，并按候选 / 实际使用 / 有冲突、需确认三种状态追溯。

## 当前不作为前置条件

- 全网实时监测和绕过登录的平台抓取。
- 多 Agent 角色编排、长期自主执行、自我进化和复杂评测平台；只有单 Agent 无法解决明确业务问题时再考虑。
- 为了“更像 Agent”迁移到 Dify 或其他编排平台。
- 用户系统、数据库、任务调度、云部署和企业权限体系；本地历史先用简单文件实现，出现真实规模需求后再升级。
- 自动发稿、自动投放、自动调整预算或自动向协作工具发送报告。
- 对效率、覆盖率、转化或营销效果作未经验证的数字承诺。
