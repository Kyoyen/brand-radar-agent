# Brand Radar

Brand Radar 是一个给营销企划人员使用的情报整理 Agent。企划人员可以先用六个问题建立本机品牌档案，也可以全部跳过、直接沿用通用 `BRAND.md`；随后说明品类、地区、竞品和本周要回答的问题，Agent 读取已经准备好的 Replay 材料和公开来源，把零散信息整理成下周可以讨论的营销机会、风险节点和 Brief 角度。

第一版要依次通过两道硬门：先证明真实 Key 能稳定跑完整链路，再证明系统会围绕营销目标形成受限调查计划、选择必要的本地查证动作、读取反馈并调整判断。无 Key 的 Mock 运行只用于检查程序链路，不能代替任何一道业务验收。

当前优先级是：用户使用 > 产品功能 > 快速成型 > 过程可复现。安全边界是基础要求，不是卖点；真正的产品亮点是目标驱动调查、受限行动、反馈调整和营销特化输出。

## 下周默认场景

2026 年 9 月 4 日的周企划会前，使用者要为 9 月 7 日至 13 日准备一份咖啡品类观察：

- 品牌：瑞幸咖啡
- 品类：现制咖啡
- 地区：全国 + 上海
- 竞品：星巴克中国、库迪咖啡、Manner、麦咖啡
- 业务问题：下周有哪些值得跟进、继续观察或主动避开的营销信号？

企划人员最终获得四类结果：按优先级排列的情报流、未来 30 天营销日历、近期重点关键词，以及 3 条有来源依据的 Brief 角度。

## 一次完整使用流程

```text
选择通用品牌档案，或通过六问补充品牌取舍
  → 确认下周业务问题
  → 读取 Replay 材料与用户提供的公开来源
  → 找到最新有效版本并排除无关或过期信息
  → Agent 逐轮选择要确认的信号和适用的营销能力
  → 读取本地查证反馈，决定继续调查还是开始成稿
  → 按品牌取舍标记机会、风险、信息不完整项和处理优先级
  → 生成情报流、日历、关键词和 3 条 Brief
  → 企划人员查看来源并决定采用、退回或继续核实
```

详细业务操作见 [下周营销企划工作流](docs/business/NEXT-WEEK-WORKFLOW.md)。

## 第一版运行口径

- 真实模型模式：从本机环境读取 API Key；`--require-api` 下缺 Key、错误 Key 或模型失败都必须明确停止。
- Replay 材料：提供稳定、可复查的输入，不冒充实时监测结果。
- 品牌档案：未建档时使用不替品牌补写人设和承诺的通用 `BRAND.md`；终端六问可逐题回答或跳过，只有确认保存后才形成本机定制档案，已有档案在本轮无新答案时保持不变。
- 营销能力：Agent 可按当前轮需要选择信号筛选、品牌契合或 Brief 转译；周会稿只显示本次实际使用的能力。
- 公开来源：可由使用者补充链接或材料；第一版不以全网实时抓取为前提。
- Mock 模式：只有未使用 `--require-api` 且本机缺 Key 时，才可进入清楚标记的程序烟雾测试；不能被展示成真实判断。
- 人工复核：品牌安全、敏感日期、低证据结论和任何对外动作都由人确认；第一版不自动发布或投放。
- Canonical 交付物：只有通过 Brand Radar 专用校验后原子保存的 JSON 才是可复查结果；本地 HTML 周会稿、未来 Dashboard / 报告都必须读取同一份 JSON，不能另写一套静态结论。
- 交互边界：当前是终端建档向导与 CLI 周企划流程，会生成本地 HTML 周会稿；还没有 GUI chat、交互 Dashboard、自动刷新或实时抓取。未来 chat 入口用于承接同一套六问、探索和追问，不能替代已校验 artifact。

## 当前状态

当前已经形成可运行的品牌驱动单 Agent 演示骨架，但仍不能称为完整自治营销产品。

企划人员可以运行 `python3 run.py --brand-setup`，围绕品牌记忆、核心人群与场景、承诺与依据、声音、热点与竞品取舍、红线与人工确认完成六问；任何一题都能跳过，首次使用且全部跳过时继续使用通用 `BRAND.md`。周企划运行时，Agent 会在信号筛选、品牌契合、Brief 转译三项营销能力中逐轮选择，查看反馈后决定继续查证或开始成稿；品牌起点、实际使用能力和“为什么继续 / 为什么停止”会进入同源 HTML 周会稿。

最新真实 DeepSeek `deepseek-v4-flash` 运行约 29.5 秒：使用通用品牌档案，完成四轮选择、三个本地调查动作和最终成稿，生成 7 张情报卡、3 条不同 Brief、JSON 与 HTML，并停在 `awaiting_human_review`，没有任何外部动作。决策路径依次核对待核的上海咖啡快闪、上海旅游节版本组和当前来源，再开始成稿；本次实际使用了信号筛选和 Brief 转译。错误 Key 约 0.9 秒以退出码 3 明确失败，没有降级 Mock，也没有增加结果文件；全量 100 项测试通过。

本次真实证据是本机忽略目录中的 `outputs/brand_radar_weekly-real-20260901-115850-982265.json` 与同名 `.html`。这些文件不随 Git 跨机器交付；新机器应使用下方命令重新生成。HTML 结构检查已经通过，但由于应用内浏览器阻止本地 `file://` 导航，本轮没有完成视觉打开检查。

关键体验修正：不要再把一句摘要措辞当作整份周报失败，也不让无卡片支撑的模型句子进入可追溯结果。JSON 和 HTML 共用一份由已校验情报卡 priority 生成的人话摘要：“本周优先讨论 / 信息不够先别拿进方案 / 明确不采用 / 继续观察”；模型的实质判断仍保留在卡片、Brief、调查动作和工具反馈中。

当前体验不是 Dify，也不是 GUI；整个流程仍不发送飞书、不发布、不投放、不改预算。

特别说明：17:50 左右曾出现由程序合成 `adjustment_reasons` 的文件，该文件不能作为 Agent 调查反馈或真实验收证据。当前有效证据以 2026-09-01 的 JSON / HTML 产物和错误 Key 失败记录为准。

## 仓库入口

- `run.py`：当前 weekly CLI 入口，同时保留旧 CLI 兼容命令。
- `framework/`：模型接入、执行循环、上下文和输出基础能力，优先复用。
- `v3_agent/tools.py`、`scenarios/tools_real.py`：当前仍被执行器引用，先作为早期工具资产保留。
- `v1_basic/`、`v2_structured/`、`v3_agent/agent.py`：演进过程参考，不是当前产品入口。
- `docs/`：当前产品、业务流程和交接事实源。

当前两个主要入口：

```bash
python3 run.py --brand-setup

python3 run.py --weekly \
  --source-pack data/replay/coffee-week-2026-09-07/manifest.json \
  --require-api
```

第一条命令不调用模型；尚无本机档案时，跳过建档即可使用通用 `BRAND.md`。第二条命令会让缺 Key、错误 Key 和模型失败明确停止，不能静默降级 Mock。需要从零准备环境时，再按 `requirements.txt` 创建本机虚拟环境。不要复制其他电脑的 `.venv`、本机品牌档案或 API Key。

下一项最小产品工作是把现有六问状态机接到轻量 GUI / chat，再用一份真实定制品牌档案复跑同一条周企划链，验证品牌取舍确实改变调查与成稿，而不是先扩成复杂 Dashboard。

## 来源边界

业务流程参考来自阿里国际 Accio 团队维护的 [RealReplicaBench 官方仓库](https://github.com/Accio-Lab/RealReplicaBench/tree/4041872837eb960a16bbe3d73b459f20680b8ad6)及其中的原始 `task.md`。这些任务在可复现的本地业务软件副本和工作空间中执行，用来检验 Agent 是否能完成长流程业务任务。

本项目只借鉴其工作方法：识别最新有效指令、跨材料核对、先读当前状态、只补缺口、保留证据、在对外动作前交给人复核。Brand Radar 的瑞幸场景、页面和输出是本项目的业务转译，不写成阿里原项目已有功能或客户落地成果。

## 第一版不做

- 绕过登录或平台限制抓取小红书、抖音等内容。
- 多 Agent 编排、自我进化、复杂评测平台、账号系统和数据库后台。
- 自动发稿、自动投放、自动改预算或自动发送飞书报告。
- 为尚未验证的效率、覆盖率或业务结果作承诺。
